Serving a static site from a Railway volume

Notes from moving a hand-built site off a laptop and onto a persistent disk.

These files were uploaded straight onto the volume mounted at /data. Nothing was rebuilt, no image was pushed, and no pipeline ran — the web server picked them up on the next request. That is the whole appeal of a plain file server: the deploy step is a copy.

What the volume buys you

A container filesystem is thrown away on every deploy. A volume is not, so the content and the code that serves it stop being the same artifact. You can redeploy the web server to pick up a security release without touching a single page, and you can change a page without waiting on a build.

  • Content survives redeploys, restarts and image upgrades.
  • The stylesheet beside this page is fingerprinted by its ETag, and comes back with a 30-day expiry.
  • Text responses are compressed on the way out; a pre-compressed .gz sibling is used when one exists.

The part that is easy to get wrong

Every volume arrives with a lost+found directory at its mount root, so the site root has to sit one level below it. Point a web server straight at the mount and the first directory listing you serve is a filesystem artefact.
